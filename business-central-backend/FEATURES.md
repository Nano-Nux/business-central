# Backend Features

This file records backend capabilities and their implementation status. Update it whenever an API, domain capability, schema, or synchronization contract changes.

| Feature | Status | Source of truth / notes |
|---|---|---|
| Go Fiber HTTP backend | Implemented for current scope | Health, authentication, authorization, user membership, catalog, POS, pricing, promotion, and inventory routes are implemented |
| OpenAPI / Swagger contract documentation | Implemented for current routes | `docs/openapi.yaml` and `docs/index.html` document health, auth, commerce, reporting, service, and repair APIs |
| Hexagonal Architecture and DDD | Implemented for current scope | Context-first packages under `internal/auth`, `internal/catalog`, `internal/pos`, `internal/operations`, `internal/reports`, and `internal/services`; global HTTP composition is under `internal/adapters/inbound/http`; compatibility DTO aliases remain only at context roots |
| Multi-tenant merchants | Implemented in schema | `merchants`, merchant-scoped foreign keys, and RLS design |
| Authentication and memberships | Implemented for current scope | Runtime login, JWT/refresh-token rotation, lockout, authorization, bootstrap, membership CRUD, and single-shop staff assignment |
| Platform-admin merchant provisioning | Implemented | `POST /api/v1/admin/merchants` creates a merchant with default roles; `POST /api/v1/admin/merchant-users` atomically creates a merchant and owner user |
| Platform currency management | Implemented | Platform-admin-only CRUD under `/api/v1/admin/currencies`; public `GET /api/v1/currencies` remains available for merchant setup |
| Merchant role management | Implemented | Platform-admin role CRUD and permission assignment under `/api/v1/admin/merchants/{id}/roles`; system role codes and deletion are protected |
| Merchant/shop module enablement | Implemented | Merchant module registry plus `shop_modules`; shop CRUD accepts and returns `module_codes` for portal gating |
| Customers and catalog | Implemented in schema | `customers`, products, variants, pricing |
| Product variant attributes | Implemented | Merchant-scoped `/api/v1/catalog/attributes` and nested value routes manage reusable TEXT/NUMBER/BOOLEAN/SELECT/DATE/JSON definitions and values; variant creation selects configured values from dropdowns and variant `attributes` are validated and synchronized through typed catalog operations |
| Product and variant images | Implemented for online API | Ordered multi-image collections support direct HTTP(S) URLs, normalized Google Drive sharing URLs, and tenant-separated JPEG/PNG/WebP/GIF uploads through SeaweedFS |
| POS catalog complexity | Implemented for web API | Merchant-level SIMPLE/COMPLEX configuration; SIMPLE product creation atomically creates its standard variant and rejects separate variant create/delete, while COMPLEX preserves the existing workflow. Deleting an unused product removes its aggregate variants and configuration; stock or immutable business history still requires deactivation instead. |
| Canonical orders and payments | Implemented | `orders`, `order_lines`, payments, refunds, server POS quotes, atomic checkout, and canonical invoice reads |
| Inventory and FIFO costing | Implemented in schema | Movement ledger, balances, cost layers, allocations |
| Storage stock checking | Implemented | `GET /api/v1/inventory/storage` provides tenant-scoped, paginated/filterable/sortable variant stock rows with RETAIL prices for merchant/staff, category hierarchy, optional product dates, staff shop-scoped quantities, and merchant-only original price/profit fields |
| Purchasing and goods receipts | Implemented | Purchase-order traceability, receivable-line discovery, direct product stock-in, optional recent-cost reuse after a variant's first receipt, idempotent atomic receipts, inventory movements, and FIFO cost layers |
| General service module | Implemented for backend scope | Service catalog, orders, appointments, billing, history, and reusable ticket/work-item form definitions and values |
| Repair module | Implemented for backend/portal scope | Repeatable work items with multi-value issues, optional conditions, automatic waiting starts, canonical waiting ends, derived day counts and whole-ticket waiting ranges; shop-scoped preset CRUD, tenant-safe child records, derived lifecycle, work-item service/part/price attribution, immediate stock/FIFO posting for Used parts, canonical payment allocations, synchronization, and work-item-aware invoices preserve compatibility aliases |
| Versioned service custom fields | Implemented for backend/portal scope | Generic and specialized ticket/work-item definitions support GENERAL, REPAIR, and CLINICAL service types, tenant-owned entity validation, versions, validation/visibility rules, printable projections, repair aggregate synchronization, portal rendering, and portal administration; mobile definition/value synchronization is excluded from this release |
| Repair-to-service-to-order relationship | Implemented | Repair -> service order -> canonical SERVICE order -> invoice and payments/refunds |
| Reports and sales analysis | Implemented | Sales summary, profit summary, UTC daily sales, top products, refunds, and FIFO cost-of-goods-sold calculations under `/api/v1/reports` |
| Cross-module transaction history | Implemented for portal scope | Shop-scoped paginated `/api/v1/transaction-history` combines stock events, canonical orders from every channel, successful refunds, and repair deposit/final checkout payments; `/{id}` resolves the event to its canonical order with line pricing, FIFO cost/profit, per-line cost-posted state, payments, and refunds |
| Stock movement detail | Implemented for portal scope | `/api/v1/inventory/movements/{id}` resolves product, variant, units, locations, current balances, receipt/purchase-order or checkout-order context, reversal links, and FIFO cost allocations without duplicating ledger data |
| Profit calculation | Implemented | Gross profit and margin use net sales minus succeeded refunds and inventory cost allocations |
| Services and repairs APIs | Implemented | Merchant-scoped CRUD plus service billing promotions, shop-scoped repair reads, canonical repair orders, stock-part consumption, repair total promotions, and repair product promotions |
| Shared collection query contract | Implemented | `query`, `filter`, zero-based `page_index`, legacy `page`, and bounded `page_size` are supported across listing endpoints |
| Public API handlers and use cases | Implemented for current scope | HTTP handlers depend on injected application ports for auth, catalog, POS, pricing, promotion, inventory, reports, services, and repairs |
| Client temporary-offline synchronization API | Partial | Authenticated handshake/push/pull/conflict routes provide idempotent typed operations, hashes, dependencies, replay results, versions, shop-filtered ordered changes, persisted checkpoints, and migrations through 0027. Settings, delivery, product metadata, product variant attributes/options, price-list/product-price lifecycle, repair aggregates/children/payments, and append-only provisional `POS_CHECKOUT` are enabled. Cash checkout reuses canonical POS/FIFO rules atomically; external payment intents require authorization. Refund, receiving/transfer/adjustment, promotion, permission/module, and remaining lifecycle policies are still rejected. |
