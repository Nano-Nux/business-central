# Portal/Mobile Parity Matrix

This is the release gate for `business-central-portal` and `business_central_mobile`. Both applications are separate clients, but they implement one operational product.

## Parity rules

Every feature must have one row here before implementation begins. A feature is complete only when its portal and mobile columns are both complete, or an intentional platform difference is documented.

The mobile foundation is a cross-cutting prerequisite rather than an
operational parity feature: its Riverpod dependency boundary and runtime-mode
validation are now implemented and tested. Operational rows below remain
partial until the matching portal workflow is implemented natively and its
offline policy is documented.

The mobile local-domain foundation also records append-only audit events for
sensitive FULLY_OFFLINE setup, authentication, staff, inventory, POS, and
repair mutations. This is a security/traceability adaptation rather than a
separate portal workflow; future synchronization must preserve canonical audit
identity and ordering.

As of 2026-08-08, the portal additionally has a typed provisional
`POS_CHECKOUT` policy with durable receipts and local stock reservation. This
does not make the POS parity row complete: mobile ONLINE temporary-offline
checkout and the shared rejected-checkout accept/revise workflow remain release
gates. See `TEMPORARY_OFFLINE_CAPABILITY_MATRIX.md`.

Repair invoice device type and brand are hidden by default and controlled by per-shop
switches under repair specifications. The portal preview, PDF, browser print,
and thermal output honor the switches; matching native mobile presentation is a
remaining repair/settings parity item.

Repair device intake now uses repeatable issues and optional repeatable
conditions. Portal intake, offline projection, preview, PDF/browser print, and
thermal output preserve both lists; native mobile intake and invoice output
preserve the lists online and in FULLY_OFFLINE storage. Merchant CRUD for the
two shop-scoped preset lists is implemented in the portal; matching native
preset administration remains a parity follow-up.

Telegram access: the portal exposes group pairing and order Confirm/Cancel only
to users with the system `merchant` or `owner` role. Staff may review groups and
orders but cannot create or rotate pairing codes, confirm/cancel orders, or
enable automatic confirmation. The backend applies the same role checks to
these tenant API actions; a future Mobile ONLINE Telegram view must mirror
them. Native Telegram remains outside the current mobile increment.

Before substantial UI work begins, define a shared design reference containing:

- color, typography, spacing, elevation, and icon rules;
- navigation and information architecture;
- buttons, inputs, selects, tables, cards, dialogs, toasts, empty states, loading states, and errors;
- POS layout and interaction rules;
- status colors and labels;
- responsive web and native-mobile adaptations;
- accessibility rules.

The design reference is the source for both implementations. Platform-specific components may differ, but their labels, hierarchy, states, and business meaning must remain equivalent.

## Feature completion gate

Before marking a feature complete:

1. The shared workflow is documented.
2. The backend API and permissions are implemented.
3. Portal and mobile screens exist.
4. Both clients use the same validation and lifecycle states.
5. Any platform difference is recorded in `UI_UX_PARITY.md`.
6. Shared acceptance scenarios pass in both clients.
7. Online, temporary-offline, and `FULLY_OFFLINE` behavior is recorded where applicable.

Telegram customer/payment behavior: each order links a canonical guest customer;
omitted names stay blank/null and `Online-Telegram-Customer` is source metadata.
Invoices are Pending until merchant confirmation atomically captures payment,
then Paid. Cancellation/expiry void pending payment. Migration 0050 preserves
existing ledgers and backfills Telegram orders without payments. Native Telegram
remains online-only and outside the native mobile increment.

Telegram quantity syntax: `qty=` and `quantity=` are equivalent in the canonical
backend parser, with exactly one quantity token per product line. The portal
guide uses `qty=` and documents compatibility with `quantity=` in every language.
Native Telegram remains outside this increment; a future ONLINE workflow must
accept both keywords with the same validation.

Telegram automatic confirmation: portal group switch defaults OFF and applies only
to new valid orders, recording Paid invoices and stock sales atomically. Existing
pending orders stay pending. The portal is the design reference; native Telegram
remains outside this increment, and FULLY_OFFLINE never contacts the backend.
Shared acceptance: backend toggle/scope/stock/payment/rollback and responsive
