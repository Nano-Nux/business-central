# Mobile Implementation Status

Last reviewed: 2026-09-23

## Current state

- Flutter project structure and platform runners exist.
- Portal WebView mode embeds the latest Next.js 16 `business-central-portal` web application inside a hardened WebView shell backed by Drift SQLite (`app.db`) and robust JavaScript channels (`BusinessCentralDatabaseChannel`, `BusinessCentralStorageChannel`, `BusinessCentralPrinterChannel`, `BusinessCentralScannerChannel`, `BusinessCentralRefreshChannel`, `NativeFileSelectorBridge`).
- Bridge scripts are injected on both `onPageStarted` and `onPageFinished` with chained callback resolver preservation (`prevResolver`), preventing race conditions during React hydration and eliminating dropped JavaScript bridge resolutions.
- JavaScript channel safety checks prevent uncaught exceptions if resolvers are invoked before registration.
- Local Drift SQLite database bridge (`NativeDatabaseBridge`) supports full canonical catalog operations (`getProducts`, `saveProduct`, `deleteProduct`), canonical customer upserts (`getCustomers`, `saveCustomer`) with idempotent record updates preserving UUID keys and timestamps, atomic POS checkout (`checkout`) with line-scoped inventory movement keys preventing collisions on multi-line same-variant purchases, provisional ID fallback, order lookup (`getOrder`, `getOrders`), setting persistence with bidirectional companion key synchronization (`bc.theme` $\leftrightarrow$ `theme`, `bc.layout` $\leftrightarrow$ `layout`), and raw SQL queries.
- Authentication synchronization bridges `bc.access_token` and `bc.merchant_id` from portal sessions into device storage and immediately triggers the `SilentLicenseValidator` heartbeat.
- Local static asset shelf server in `PortalBundleManager` supports WebP, WOFF, WOFF2, TTF, and WebAssembly MIME types for embedded portal bundles.
- Platform runners gracefully fall back from `.env` to `.env.example` if no custom `.env` is present.
- Riverpod and dotenv bootstrap are implemented.
- Runtime configuration accepts case-insensitive `ONLINE`, `OFFLINE`, and `FULLY_OFFLINE` values and fails closed for missing/invalid modes.
- `FULLY_OFFLINE` omits the backend URI and injects a network-denying client; production ONLINE HTTP URLs are rejected.
- Drift schema version 27 and typed forward migrations/transactions are implemented for the local tenant/auth/module/device/session/entity-version/checkpoint/queue foundation, local identity contact fields, merchant/shop-scoped catalog/measurement/delivery/settings tables, local price-list/price tables, local POS order/payment/refund/promotion tables, local inventory ledger/FIFO cost layers and allocations, purchase-order/receipt/batch/expiry movement context, exact order-line discount/tax fields, append-only local audit events, device-local thermal printer profiles, payload-preserving canonical records with tombstones, local service records, and local repair records with repeatable work-item ticket/child/custom-field projections. An authenticated merchant-scoped JSON backup/restore service validates format/schema/scope, includes local settings, pending operation rows, operational measurement, delivery, pricing, inventory costing, payment/refund, promotion, audit, service, repair, and canonical records, and excludes credentials/authorization assignments and Bluetooth addresses.
- Fully offline first-run owner provisioning and local staff provisioning/login use Argon2id with unique salts and never contact the backend; staff memberships, shop assignment, active state, and role assignments remain merchant-scoped in Drift.
- The FULLY_OFFLINE Staff destination now remains visible for local owner administration. Existing local permission definitions can be assigned to merchant-scoped roles, merchant-enabled modules can be enabled/disabled per shop, repository-level `rbac.manage` checks protect those writes, and the authenticated local shell refreshes authorization after each change; permission-definition creation and ONLINE reconciliation remain pending.
- Fully offline sensitive mutations record append-only local audit events for owner setup/login, staff changes, inventory receipts/FIFO sales, POS checkout/refunds, and repair intake/status/diagnostics/payments/refunds; audit writes share the domain transaction where the mutation is transactional and are merchant/shop/actor scoped.
- ONLINE login, refresh rotation, current-user hydration, and logout use the backend OpenAPI contract; tokens are stored through platform secure storage.
- ONLINE connectivity readiness, transport hard-stop, merchant/shop hydration, tenant-scoped cache writes, staff shop lock, and adaptive guarded shell navigation are implemented.
- The first ONLINE catalog read surface uses `/catalog/categories` and `/catalog/products` through a repository/controller boundary and native searchable list; successful reads are persisted by merchant scope and transport-denied reads use the cache. Product variant detail reads use `/catalog/products/{id}/variants` with merchant validation.
- Permission-gated native catalog administration now creates/updates/deletes categories and products and creates/updates/deletes variants through the backend catalog contracts; the native catalog screen exposes guarded create/delete actions while read-only staff retain the search/detail surface.
- The native Catalog destination exposes permission-gated unit and conversion administration through the canonical `/units` and `/unit-conversions` contracts; FULLY_OFFLINE unit storage, conversion validation, and local create/delete workflows are durable, while cross-domain synchronization remains pending.
- The native Pricing destination lists/creates/deletes price lists and reads/upserts/deletes variant prices through `/pricing/price-lists` and `/pricing/prices`; FULLY_OFFLINE uses a durable local price-list/price layer and applies local price writes to the POS variant catalog; price scheduling remains pending.
- The ONLINE POS surface uses shop-scoped `/pos/catalog`, backend-authoritative `/pos/quote`, idempotent `/pos/orders` checkout, and `/pos/orders/{orderId}/refunds` with captured-payment limits, assigned-shop scope, and idempotency. FULLY_OFFLINE POS uses the local catalog, exact local totals, atomic local orders, FIFO stock consumption, captured local payment records, idempotent local refund records, and the exact invoice projection; only ONLINE temporary-offline financial mutation policies remain pending.
- The ONLINE inventory slice reads `/inventory/locations`, filters the selected shop, and persists the merchant/shop-scoped result in the existing SQLite locations table for transport-denied fallback. Permission-gated stock receiving posts `/inventory/stock-in` with a backend idempotent event key. Selected-shop movement history filters immutable ledger rows by scoped location IDs, and movement detail reads resolve product/location/document/current-balance/FIFO context. FULLY_OFFLINE inventory records exact local stock receiving with purchase-order/receipt/batch/expiry context, FIFO layers/allocations, POS and repair-part stock-out movements with idempotent event keys, balance updates, and local movement detail; transfer/adjustment parity and ONLINE offline mutation remain pending.
- The native Reports screen reads `/reports/sales-summary`, `/reports/sales-by-day`, and `/reports/top-products` for the selected shop and exact response strings. FULLY_OFFLINE derives local summary/day/top-product reads from local orders and FIFO allocations, including refund-adjusted COGS, gross profit, and margin for tracked stock; cache freshness and untracked-stock provenance remain pending.
- The native History screen reads `/transaction-history` with shop/event/date/search filters and loads `/transaction-history/{id}` into a detail sheet with order lines, FIFO costs, profit, payments, and refunds; POS payment refunds are actionable through the canonical command. FULLY_OFFLINE lists local order, inventory movement, POS refund, and repair checkout/refund events with local FIFO cost/profit, receipt context, captured-payment projections, and exact invoice/thermal print actions; backend reconciliation and richer detail presentation remain pending.
- Delivery management reads `/shops/{shopId}/deliveries` and uses `/deliveries` create/delete with merchant/shop payload validation; POS quote/checkout includes the selected delivery ID. FULLY_OFFLINE delivery options and selected IDs are merchant/shop-scoped SQLite data with backup/restore coverage; temporary-offline synchronization and fee policies remain pending.
- The native Invoices screen reads `/invoices`, filters by the selected shop, preserves exact totals and line quantities, and presents invoice details. FULLY_OFFLINE uses local order/line and repair service/part projections with an explicit standalone footer. Native PDF generation, share, OS print, and image-first Bluetooth ESC/POS thermal actions use the same exact invoice projection for sales and repairs; canonical numbering and reconciliation remain pending.
- The native Customers screen derives a view-only selected-shop projection from `/invoices` and `/repairs/orders`, combining sales and repair counts without introducing a competing customer model; FULLY_OFFLINE combines local order and local repair counts, while customer CRUD remains pending.
- The native Repairs screen lists selected-shop tickets and submits the backend atomic `/repairs/tickets` command with device, customer, issue, priority, fee, note, stable work-item IDs, and idempotency fields. It also supports repeatable device intake sections. Ticket details read/create diagnostics, idempotent deposits/final payments, scoped/idempotent refunds, parts, device images, approvals, warranties, and lifecycle status through backend contracts; FULLY_OFFLINE stores those child records in the merchant/shop-scoped local repair ledger with balance-checked local payment/refund records, validates work-item references, consumes FIFO stock for used catalog parts, recalculates part-based totals, and performs no external payment capture. Repair invoice projection/printing is available locally; ONLINE temporary-offline ticket CREATE and dependency-ordered supported child CREATE operations reconcile through typed sync with canonical work-item IDs. External methods and promotion redemption remain online-only.
- The shared repair repository contract accepts repeatable `RepairWorkItemInput` values and exposes `listWorkItems` and backend-defined `RepairFormField` definitions. ONLINE includes complete ticket/work-item field values and stable client IDs in the atomic ticket request, reads `/repairs/orders/{id}/work-items`, and caches form definitions in canonical storage; FULLY_OFFLINE reads cached definitions, stores ticket plus additional device/issue/custom-field children under the local repair record, exposes the same aggregate shape, and includes child details and printable fields in local invoice lines. Reconnect sync applies server-authoritative totals and canonical work-item/device/child projections; ticket-level billing remains the current boundary.
- Repair work-item inputs and projections preserve ordered repeatable issues and
  optional repeatable conditions in ONLINE requests, FULLY_OFFLINE records,
  invoice preview, PDF/OS printing, and thermal output. Empty conditions are
  omitted. Canonical shop-level Issue and Condition preset administration is
  available in the portal Repairs subpages; a native preset CRUD surface remains
  an explicit portal/mobile parity follow-up.
- The native Settings screen reads and updates selected-shop name, code, timezone, tax, and receipt/footer notes through `/shops/{id}` for `membership.manage`; FULLY_OFFLINE persists the same merchant/shop-scoped values locally; device-local Bluetooth printer pairing/profile settings and local shop-scoped repair fault presets/default duration are implemented. Repair specifications remain local-only because the portal currently stores them in browser-local settings and the backend exposes no canonical contract.
- The native Staff destination uses the canonical `/users` and `/roles`-compatible membership contract for ONLINE list, create, activate/deactivate, and delete actions under `membership.manage`; FULLY_OFFLINE uses the local identity/membership/role graph for scoped staff provisioning, Argon2id password updates, shop assignment, active-state changes, role-permission editing, and shop-module controls, while permission-definition creation and reconciliation remain pending.
- The native Promotions screen lists, creates, and removes backend promotion definitions for `tenant.write`, including schedule and usage-limit fields; native detail controls manage promotion codes and product/variant scopes, and POS quote/checkout can carry the selected promotion ID. FULLY_OFFLINE has the same local catalog/scope/code workflow with schedule, minimum, usage-limit, exact POS discount/tax validation, and product/variant-scoped repair-part discount/redemption; standalone local service billing rejects promotion application until a canonical order relationship exists, and ONLINE temporary-offline promotion synchronization remains pending.
- The native Services destination is module- and permission-gated, lists the merchant service catalog, creates/removes service definitions, lists only the selected shop's service orders, creates service orders, reads/adds service-order items, and reads/adds appointments, notes, and billing records. Repository/controller contracts pair service catalog/order/item/appointment/billing updates and deletes to backend routes, while FULLY_OFFLINE uses the same typed workflow against durable merchant/shop-scoped local service records; local billing is standalone and does not capture external payments.
- ONLINE temporary-offline shop settings, repair-ticket CREATE, and supported repair-child CREATE operations commit local projections and queue rows with payload hashes. Riverpod starts a reconnect worker that performs the backend handshake, uploads dependency-ready rows in parent-before-child order, records accepted/rejected/conflicted outcomes, applies server settings and repair ticket/child projections, and advances a durable merchant checkpoint after transactionally applying pull pages. The settings screen surfaces queued rejection/conflict counts.
- `ExactMoney` represents decimal amounts with `BigInt` minor units and is covered by parsing/arithmetic tests.
